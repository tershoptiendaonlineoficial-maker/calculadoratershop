2. JUSTIFICACIÓN MATEMÁTICA — TRIPLE PERSPECTIVA CAMBIARIA
────────────────────────────────────────────────────────────
  El ecosistema venezolano opera bajo tres sistemas de valoración del
  USD simultáneos. La omisión de cualquiera de ellos introduce sesgo
  contable. La arquitectura v4.0 implementa tres conversiones paralelas:

  ┌─────────────────┬────────────────────────────────────────────────┐
  │ Canal           │ Justificación Matemática                       │
  ├─────────────────┼────────────────────────────────────────────────┤
  │ BCV — USD/Bs.   │ Base legal. Obligatorio para facturación formal │
  │                 │ y liquidaciones contractuales. Referencia del   │
  │                 │ Banco Central de Venezuela (Art. 5, Ley BCV).   │
  ├─────────────────┼────────────────────────────────────────────────┤
  │ BCV — EUR/Bs.   │ Relevancia operativa para proveedores con       │
  │                 │ insumos importados de la zona euro. Permite al  │
  │                 │ revendedor comparar si conviene liquidar en EUR  │
  │                 │ o USD cuando el cliente paga en euros.           │
  ├─────────────────┼────────────────────────────────────────────────┤
  │ Binance P2P     │ Tasa de mercado real. Refleja el poder de       │
  │                 │ compra efectivo del bolívar en operaciones       │
  │                 │ crypto-to-fiat. Diferencial promedio ≈ 3-6%     │
  │                 │ sobre la tasa BCV oficial, factor crítico para   │
  │                 │ decisiones de cobro en efectivo vs. transferencia│
  └─────────────────┴────────────────────────────────────────────────┘

  Fórmula de conversión aplicada uniformemente:
    Monto_Bs = Monto_USD × Tasa_Canal
  
  Formato de salida contable (ISO venezolano):
    Separador de miles  → Punto    (.)
    Separador decimal   → Coma     (,)
    Ejemplo: 1.523.450,75 Bs.

3. MATRIZ EDITABLE DE PRECIOS EN CALIENTE (HOT RELOAD)
────────────────────────────────────────────────────────
  Descripción: La matriz de 9 productos expone inputs numéricos nativos
  directamente ligados al arreglo `products[]` en memoria mediante el
  handler `updatePrice(idx, field, val)`.

  Mecanismo de propagación:
    Input → onchange → products[i][campo] = safeNum(val)
                     → refreshRowOptions()
                     → recalc()

  Política de seguridad NaN:
    Toda captura de valor numérico pasa por:
      safeNum(v) = parseFloat(v) || 0
    Esto garantiza que ningún campo vacío o malformado genera NaN
    en cascada hacia los resultados del tablero.

4. MOTOR DE FÓRMULAS v4.0 — AUDITORÍA MATEMÁTICA
──────────────────────────────────────────────────
  Variables base por fila i:
    qty_i   = cantidad de prendas
    prov_i  = costo proveedor unitario
    sale_i  = precio de venta unitario (detal o mayor)

  Agregados:
    totalCostProv   = Σ(prov_i × qty_i)
    totalVentaBruta = Σ(sale_i × qty_i)
    totalQty        = Σ(qty_i)

  Promo (afecta SOLO ingresos del revendedor, costo proveedor intacto):
    · Modo %:    clienteBase = totalVentaBruta × (1 − disc/100)
    · Modo fijo: clienteBase = precioFijoUnitario × totalQty

  Diseños adicionales:
    designExtra = (dCatalog×0.60 + dCustom×0.75) × totalQty

  Delivery (pass-through, no altera margen):
    delivery = {pickup:0, avenida:1.00, domicilio:inputUsuario}

  Resultados finales:
    ① Proveedor  = totalCostProv
    ② Ganancia   = clienteBase − totalCostProv
    ③ Cliente    = clienteBase
    ④ + Delivery = clienteBase + delivery
    ⑤ Gran Total = clienteBase + delivery + designExtra

  Verificación de consistencia:
    ③ ≤ ④ ≤ ⑤    SIEMPRE (delivery ≥ 0, designExtra ≥ 0) ✓
    ② = ③ − ①   cuando no hay promo ✓
    ① permanece invariante ante cualquier promo ✓
